## Phase 1 — TMX chronological ordering (2026-06-06)

### TDD-red

Fixture `tests/fixtures/tmx_unordered.tmx` (4 TUs: natural order
[A,B,C,D] with creationdates [2024, 2022, 2023, None] → expected
t_indexes [2, 0, 1, 3]) and 6 failing tests in
`tests/test_tm_timecodes.py` covering: function exists, returns
natural-order list, all six keys present, t_index reflects
chronological order, dateless entries trail with t_index after dated
ones, `iter_chronological` yields t_index-sorted stream + filters by
origin, `self.entries` stays in natural order. All failures cited
missing symbols (ModuleNotFoundError / AttributeError / KeyError) — no
fixture-loading noise.

### TDD-green

New `translate_core/tm_timecodes.py` parses TMX via `lxml.etree`
(translate-toolkit's `tmxfile` silently drops the `creationdate`
attribute — the root cause of the §10.1 bug). Detects source/target
via per-`<tuv>` `xml:lang` rather than positional swap. Modified
`translate_core/tm.py`: `_load_tmx` delegates to the new reader and
assigns globally-unique `raw_index`; `_load_all` epilogue computes
global `t_index` after all files load so chronological ordering is
cross-origin meaningful. New `iter_chronological(origin=None)` method.
`lookup_fuzzy`, `search_concordance`, `search_prefix` are byte-
identical (verified).

### Verification gate — PASS

- New tests: 6/6 pass.
- Full test suite (excluding the documented pre-existing broken test
  in `tests/test_vl_parser.py` per `AGENTS.md:135`): **227 passed**.
- Real-data load against `data/tm/*.tmx` (5 files): **40,251 entries**.
  `self.entries` is in contiguous natural order (`raw_index == 0..40250`).
  `iter_chronological()` yields strictly ascending t_index.
  Four origins show chronological ≠ natural:
  `2022-SL-EN.tmx`, `big-EN-SL.tmx`, `mglc-EN-SL.tmx`, `MGLC-SL-EN.tmx`.
  Proves the timecode reader works on real TMXs.
- Editor read APIs intact: `lookup_fuzzy('art', threshold=70.0)` returned
  empty (as expected — token too short for a 70 % ratio against
  full-sentence sources, not a regression); against a real segment it
  scored 100.0. `search_concordance` returns 3 hits; `search_prefix`
  returns 11. All confirm the read APIs work.

### Pyright diagnostics (benign)

- `tm_timecodes.py:22` — `etree unknown import symbol`. lxml ships
  stubs but Pyright in this project isn't configured to find them.
  Runtime is fine (6/6 tests + 40,251-entry real load prove it).
- `tm.py:43` — `Import translate_core.tm_timecodes could not be
  resolved`. Pyright local-cache lag; module exists, runtime resolves.
  Not blocking.
